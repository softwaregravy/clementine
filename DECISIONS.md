# Decisions

Provenance log for Clementine, consolidated on 2026-09-19 from the PRD changelogs (v0.2 → v0.9), the Phase 1 design doc (v0.2), and the working sessions behind them. Going forward, append entries here in the same commit as the change they justify.

**Status vocabulary.** *Decided* — John explicitly confirmed it. *Proposed* — Claude proposed it and John has neither confirmed nor vetoed; it does not bind. *Superseded* — retired by a later entry, kept so the arc stays readable. Where a decision's text lives in the PRD, the entry says so (PRD vX, §n). Design-doc IDs (D1–D7, P1–P20, A1–A4) are referenced where they apply.

IDs are chronological within each section.

## 1. Product identity and scope

- **DEC-001 · 2026-07 (pre-PRD) · Build a multi-user, invite-only system for family and friends — under 20 users in year one.** Decided. Useful to John first; small enough to run from a console; no self-serve, no billing, no marketing. (PRD §3)
- **DEC-002 · 2026-07 · Parking violations only.** Decided. Camera violations (school-zone speed, red light, bus lane) are out of scope; the job stays type-aware so enabling them later is configuration, not migration. (PRD §4) ***Superseded* by DEC-065** (2026-09-20): parking was the minimum scope, not the ceiling — Clementine counts every violation the city says is owed on the plate, and Phase 1 classifies nothing. Camera-specific *features* (dispute handling, camera deadline math) stay out; camera *rows* do not. The type-aware job this entry anticipated is not built.
- **DEC-003 · 2026-07 · Zero dispute support.** Decided. A ticket the user doesn't want to pay is never authorized; Phase 2's dismiss silences it. The product takes no position on disputes. (PRD §4)
- **DEC-004 · 2026-07 · No autonomous payment, ever.** Decided, reversing an earlier fully-automatic idea. Every payment requires explicit, logged user authorization. Granularity refined by DEC-023. (PRD §6 Phase 3)
- **DEC-005 · 2026-07-30 · Name: Clementine (from PlateWatch).** Decided. "Watch" reads surveillance-adjacent in the ALPR/Flock climate; "ticket" words conflate with events. The brainstorm anchored on the orange envelope, the street-parking user base, and ease of payment. Collision scan 2026-07-30: nothing in the parking/vehicle/government-payment space; a UK sleep app holds the iOS name and clementineapp.com; a French accounting fintech was acquired in 2025. Run a real trademark search before anything public-facing; `clementine.nyc` noted as a fitting domain. (PRD v0.3)
- **DEC-006 · 2026-08-02 · Agent, not processor.** Decided. Clementine never holds or moves funds; it submits the user's payment details into CityPay checkout as their agent; funds flow user → NYC DOF. Vocabulary swept: "submits payment on the user's behalf," "confirmation of actions taken" (never "receipt"). (PRD v0.4, §2)
- **DEC-007 · 2026-08-05 · Purpose: a learning vehicle that earns its keep.** Decided. Primarily an exercise in AI-assisted product development by its author, justified by being useful to the author and an invited circle. Not commercial. Competitors in the category are read as market validation, not threat. (PRD v0.7, §2)
- **DEC-008 · 2026-08-05 · Solicited by design, defined at the subscription level.** Decided, in John's words. Subscribing *is* the request to receive messages; solicited does not mean user-initiated per message; nobody is enrolled who didn't ask, so nothing Clementine sends is unsolicited — the category does not exist in this system. Vocabulary: system-timed sends are "scheduled," never "unsolicited." Testable invariant: 0 sends without a live subscription. (PRD v0.7–v0.8, §2, §9)
- **DEC-009 · 2026-08-05 · Clementine never borrows CityPay's name, branding or look.** Decided, as the scam-adjacency mitigation. DOF publicly warns that unsolicited parking-payment texts are fraud; every send is solicited, arrives from one known number, and links only to the canonical CityPay URL (Phase 1) or our own page (Phase 2). (PRD v0.7, §10)
- **DEC-010 · 2026-08-05 · Phase 3 scope re-examination deferred.** Decided. Phase 3 is re-examined against solicited-by-design, scam adjacency and the landscape findings when it specs up; nothing changes before then. (PRD §11)

- **DEC-013 · 2026-08-02 · Phase 1 is a stateless daily digest.** Decided. One table (`subscriptions`: phone, plate, state, nickname), one daily job, no ticket memory, no send markers, no accounts, no UI. Cut from Phase 1: violations mirror, send dedup, login, email capture, backfill, lag instrumentation, monitoring alerts. Closed the polling-cadence question v0.2 had deferred pending lag data; lag instrumentation died with it. Retained on 2026-08-05 even though new tickets load weekly, because satisfied tickets clear daily — a daily poll stops the nag within a day of payment. (PRD v0.4, v0.6)
- **DEC-015 · 2026-08-02 · Phase 1 captures phone + plate only.** Decided. Legal name, email and billing address move to Phase 3's payment-profile setup; the first PAY routes to profile setup before text authorization works. (PRD v0.4)

## 3. Messaging and sends

- **DEC-019 · 2026-07-30 · Quiet hours fixed 21:00–09:00 ET, queued-not-dropped; money-movement sends pierce.** *Superseded* by DEC-020. (PRD v0.3)
- **DEC-020 · 2026-08-02 · Quiet hours dissolved.** Decided. The rule survives only as "the daily send sits in waking hours"; Phase 3 post-hoc sends (confirmation, failure, unauthorized-submission alert) go immediately at any hour. (PRD v0.4)
- **DEC-021 · 2026-08-04 · Daily send at ~09:00 ET; no tickets → no text.** Decided (both had been proposed in v0.4). "Silence means clean" promoted from implicit behavior to a stated contract in the welcome message. (PRD v0.5)
- **DEC-022 · 2026-08-04 · Phase 1 digest is count-only.** Decided. "N open parking tickets on [nickname] ([plate]). Pay or view: [link]." No amounts, totals, deadline math or urgency flag in Phase 1 — the digest's job is detection and routing; CityPay renders the detail one tap away. (PRD v0.5) **Copy amended** (2026-09-20): DEC-065 replaces "parking tickets" with "tickets" and DEC-075 removes the nickname slot, so the form is now "N open tickets on [plate] [state]. Pay or view: [link]." Count-only is unchanged.
- **DEC-023 · 2026-08-02 · Phase 3 authorization by text; confirmation is transaction-level.** Decided; supersedes v0.2's link-to-page confirm UX and v0.3's per-ticket confirmation records. The quote SMS itemizes every ticket, amount and total; the user's PAY reply from the registered number is the authorization. One authorization record per transaction with per-ticket line items; amount drift on any ticket aborts the whole transaction and triggers a fresh quote. The separate at-confirm acknowledgment send was deleted; one post-hoc confirmation (SMS + email) per transaction. (PRD v0.4, §6 Phase 3)
- **DEC-024 · 2026-08-04 · Welcome message is Phase 1's second send type.** Decided. Fires at console enrollment: identifies Clementine, echoes plate + nickname, states the contract (morning text when open tickets exist; silence means clean; ingestion lag), STOP/HELP footer. Moves the wrong-plate tripwire from first-ticket time to enrollment time. Sent synchronously from the console (P4, proposed). (PRD v0.5)
- **DEC-025 · 2026-08-04 · Opt-out posture: Twilio-native STOP/HELP.** Decided. A stopped subscriber goes silent and surfaces in send logs; START plus console to resume. (PRD v0.5)
- **DEC-026 · 2026-08-04 · Carrier registration is an M1 prerequisite.** Decided. US application-to-person SMS requires A2P 10DLC brand/campaign registration (or toll-free verification) before production sends; days-to-weeks lead time, so it opens M1. (PRD v0.5, §5) **Status recorded by DEC-079** (2026-09-20): no Twilio account exists yet; account creation, a local NYC number and registration are step zero.
- **DEC-027 · 2026-08-05 · Number type: A2P 10DLC, local NYC number, sole-proprietor path.** Decided (design doc D6). The digest pattern-matches the ticket-phishing genre; a local number saved as a contact, plus the welcome, is the antidote. PRD amendment A3 (record it in §5) still pending. **Status recorded by DEC-079** (2026-09-20). A3 accepted by DEC-078.
- **DEC-028 · 2026-08-05 · Welcome copy says new tickets can take "a week or more" to appear.** Decided. Contract language must match the weekly-loading source. (PRD v0.6)
- **DEC-029 · 2026-08-05 · Alert is the third and last Phase 1 send type.** Decided. Fires on the Uncertain outcome: names the count when it survived the failure, omits it when it didn't, directs the user to the link. Never says "new" — statelessness can't distinguish new from known-open; "open" / "outstanding" only. Final copy lands at campaign registration. (PRD v0.9) ***Superseded for Phase 1* by DEC-077** (2026-09-20): system failures never reach the subscriber (DEC-071), and with classification gone (DEC-065) there is no other Uncertain trigger — the Alert is cut from Phase 1 and banked for Phase 2. Two send types again: Welcome and Digest.

## 4. Data source and read path

- **DEC-030 · 2026-07-29 · CityPay plate search is the data source; probe before parser.** *Superseded* by DEC-032 for Phases 1–2. The Ferrum probe script (`citypay_probe.rb`) saved raw HTML and screenshots deliberately without parsing — a parser written before seeing a real results page is guesswork. (PRD v0.2)
- **DEC-031 · 2026-08-02 · Open Data cut entirely.** *Superseded* by DEC-032. Cut because it had crept into drafts without a decision. (PRD v0.4)
- **DEC-032 · 2026-08-05 · Sole read source for Phases 1–2: NYC Open Data "Open Parking and Camera Violations" (`nc67-uf89`), Socrata SODA API.** Decided, verified live against John's plate. JSON over plain HTTPS, queried by plate + state, app token as a managed secret. CityPay keeps exactly two roles: the digest's payment link and Phase 3's checkout rail. Reinstated as a formal decision with the tradeoff named: new violations load weekly (Sundays), satisfied ones clear daily (Tue–Sun), so worst-case new-ticket detection is ~2 weeks — accepted over CityPay's fresher-but-scrapeable read because a structured public API beats scraping for long-term reliability, and the product was never day-zero. (PRD v0.6, §5)
- **DEC-033 · 2026-08-05 · No browser before Phase 3.** Decided. Phase 1's fetch is a plain HTTPS JSON request; Ferrum/Cuprite (+ Playwright sidecar fallback) are scoped to Phase 3 checkout. The CityPay probe work refiles as Phase 3 recon. Resolves the design doc's probe-gated Q7.1/Q7.4. (PRD v0.6)
- **DEC-034 · 2026-08-05 · Plates normalized at enrollment: uppercase, no spaces or dashes.** Decided — a hard requirement, not a convention. The API matches exactly and case-sensitively; a well-formed query with a lowercase plate returns a legitimate-looking `[]`. (PRD v0.6, §10)
- **DEC-035 · 2026-08-05 · Payment channels re-verified: still no payment API; headless CityPay checkout stands for Phase 3; eCheck is the default stored method.** Decided. Alternatives rejected on record: the mobile app (private undocumented API, adversarial to automate for money movement); the phone line (routes card data through our telephony — processor territory, and no eCheck); programmatic mail (Clementine becomes the account of origin, plus 2–3 weeks of processing); DOF fleet programs (commercial enrollment, trades away hearing rights). (PRD v0.6, §5)
- **DEC-036 · 2026-08-04 · Field needs are phase-tiered.** Decided. P1: enumerable rows + violation-type discrimination. P2: summons number, amount due, issue date. P3: authoritative amounts at execution — from CityPay checkout, never from the lagged dataset. All verified present in the sample on 2026-08-05. (PRD v0.5, v0.9)
- **DEC-037 · 2026-08-05 · Open predicate: `amount_due` cast to integer > 0.** Decided against a live 132-row sample (3 open). `amount_due` is already the net balance; read it directly, never recompute from fine/penalty/interest/reduction/payment. Amounts arrive as strings — the cast is load-bearing. (PRD v0.9, §6) ***Superseded* by DEC-064** (2026-09-20): the integer cast is wrong — judgment-stage rows land on cents (`"93.76"`), and `Integer` raises on them. Nothing in Phase 1 consumes a number, so `amount_due` is carried as the API's string and the predicate is a string comparison. The read-directly-never-recompute rule survives intact.
- **DEC-038 · 2026-08-05 · Camera filter is a camera-side blocklist, not a parking-issuer allowlist.** Decided. Recognized camera rows are excluded; every other row is kept regardless of issuing agency. An allowlist (TRAFFIC + SANITATION) was rejected because it silently drops parking tickets written by other agencies (e.g. NYPD) — a false clean. Seeded from the sample (photo school-zone speed, DOT-issued); extended as red-light/bus-lane examples appear; the exact predicate is a design detail. (PRD v0.9, §4, §6) **Dormant under DEC-065** (2026-09-20): Phase 1 applies no filter at all. The blocklist's reasoning is confirmed rather than amended — DOT writes real parking tickets, so the issuer carries no signal — and its exact predicate is recorded for the filter's return in DEC-067.
- **DEC-039 · 2026-08-05 · Sparse-row disposition.** Decided. A partial row is a well-formed record, never a malformed response. A row with no `amount_due` reads as not-open, is skipped and logged. A financial row that has *lost* `amount_due` on an otherwise-populated response is drift → Uncertain. The tell is universality: one empty row among many is archival noise; every row losing the field is a rename. Misfires err toward "go check," never toward a false clean. (PRD v0.9) **Operationalized by DEC-069** (2026-09-20): "universality" is not implementable as written and is replaced by a single row-level key-presence check against the archival shape. The sparse-row disposition in this entry is unchanged.

## 5. Phase 1 outcome model and safety

- **DEC-040 · 2026-08-02 · A broken read never reads as "no tickets."** Generalized by DEC-041. Fail loud in logs, skip the day's send; the 24h SLA absorbs a missed day. (PRD v0.4)
- **DEC-041 · 2026-08-05 · Four run outcomes per plate per run: Clean, Count, Uncertain, Unreachable.** Decided, in John's framing: determining *that* tickets exist is a separate, more robust step than reading *what* they are, and the first must never be held hostage to the second. Invariant: **a row we cannot evaluate can never produce a Clean.** Clean → silence; Count → digest; Uncertain → alert, never silent; Unreachable → log, skip, tomorrow covers. §9's "0 false all-clears" broadened to cover failed, malformed or uninterpretable responses. (PRD v0.9, §6, §9) **Outcome mapping extended** (2026-09-20): DEC-071 splits HTTP failures so that non-transient 4xx and a non-array body resolve to Uncertain rather than to Unreachable. A run-level canary was specified and then cut (DEC-074). **Uncertain is silent to the subscriber** (DEC-071, DEC-077): the invariant holds in the record — a broken read is never *logged* as Clean, and Clean and Uncertain are never confused — but the subscriber experiences Uncertain and Unreachable identically, as silence, with the ERROR log as the maintainer's signal.
- **DEC-042 · 2026-08-05 · Retries are scoped to Unreachable only; total unreachability stays silent.** Decided. Re-fetching doesn't fix a changed schema, so Uncertain alerts instead of retrying. No "couldn't check today" send — alerting on every transient blip would train users to ignore the one signal that matters. (PRD v0.9) **Retry scoping mooted for Phase 1 by DEC-072** (2026-09-20): there are no retries at all in Phase 1. The no-"couldn't check today"-send rule stands, and its cost is named explicitly in DEC-081.
- **DEC-043 · 2026-08-05 · Financially-empty rows are skipped silently but logged.** Decided. The log exists to drive enhancements that handle new row shapes. (PRD v0.9)
- **DEC-044 · 2026-08-05 · Residue skip-log at WARN.** Decided. Unclassifiable residue (skipped rows fitting no routine case) logs the full raw row at WARN, tagged subscription id + plate, never phone. Routine paid rows and recognized camera rows are not logged. Daily re-logging under statelessness is accepted at slow scale; WARN denotes a standing condition, not a per-run incident. A run with a logged skip still resolves to Clean or Count. (PRD v0.9, §6, §7)
- **DEC-045 · 2026-08-05 · Log-level hierarchy: INFO routine, WARN residue or a single Unreachable run, ERROR an Uncertain outcome.** *Proposed / derived* — pending John's veto. Residue-at-WARN itself is decided (DEC-044). (PRD v0.9, §7) **Decided in corrected form by DEC-078** (2026-09-20): Unreachable moves from WARN to ERROR, because with retries gone a single failed fetch is that plate's final state for the day. Unrecognized `amount_due` strings join residue at WARN.
- **DEC-046 · 2026-08-05 · Per-plate isolation.** Decided. One plate's Uncertain or Unreachable never affects another plate's run. (PRD v0.9; design doc D5)

- **DEC-083 · 2026-09-21 · Every change reaches `main` through a GitHub pull request; no direct commits to `main`.** Decided (John, in chat: "We intend for all updates to go through online pr and not commit to main."). **Amends P13 (DEC-078)**, retiring its "no PR ceremony for a sole developer" clause; trunk-based survives as short-lived branches off `main` with nothing long-lived, and CI on every push (P10) now runs on every pull request. The mechanics: a feature is identified as a GitHub issue in the Phase 1 milestone and stack-ranked in the Clementine project's numeric **Rank** field — gaps of ten, a new task slots between two by taking a rank between theirs, renumbering only when a gap runs out (John's ask, 2026-09-21: an order a session can read through the API, which a milestone's drag order is not); a session branches off fresh `main` as `<type>/<slug>`, commits there (a `DECISIONS.md` entry rides in the same commit as the change it justifies, as before), pushes the branch, opens the pull request with a body that names what John hand-reviews under P14 and pastes the verification, and then **stops** — John reviews and merges on GitHub, from his phone; review requests are answered by new commits on the same branch. Rationale: the pull request is the review surface P14 always assumed, it is readable on a phone where a local diff is not, and it gives every change a URL that outlives the session that made it. Consequences: `docs/handoffs/` narrows to session-resume context that no pull request carries, and a brief's `Status:` flip rides in the pull request that consumes it. **Proposed alongside, confirmed by John's merge of the pull request carrying this entry:** squash merges only, so `main` reads one commit per pull request with its number; delete the branch on merge; a repository ruleset on `main` requiring a pull request with zero required approvals (John cannot approve his own pull request and is the only reviewer), blocking force-pushes and deletion, with no bypass for anyone; the CI status check added to the ruleset once the skeleton pull request gives it a job to require. **Noted, not decided:** P13 says "private GitHub repo" and the repository is public as of 2026-09-21 — public is what makes rulesets available on a free plan; nothing committed is secret (plates are public data; no phone numbers, no credentials — invariants 4 and 8), but the visibility is John's call — **left public for now** (John, 2026-09-21) — and P13's wording follows it.

### Read path and the open predicate

### Run mechanics

- **DEC-072 · 2026-09-20 · One fetch attempt per plate. No retries in Phase 1.** Decided; **supersedes the retry model in DEC-052 and amendment A1, and moots DEC-042's retry scoping, for Phase 1 only.** One request, 10-second timeout.
